## 1. Mission

This is a **release-candidate hardening task**, not a feature-expansion task.

The current AxiomFig architecture is already the preferred architecture. Do not reorganize production modules merely to look more "standard". Treat the existing structure as frozen by default:

```text
axiomfig-skill/
├── SKILL.md
├── references/
├── src/axiomfig/
│   ├── templates/
│   └── resources/
├── examples/
├── scripts/
├── tests/
├── gallery/
└── reports/
```

The central objective is to use **tests and executable quality gates to constrain architecture, expose hidden failure modes, and prevent future regressions**.

Production code or architecture may change only when a test, static analysis result, package-isolation check, or independent audit demonstrates a real defect or ownership problem.

The project philosophy remains:

```text
scientific meaning      -> Agent
public semantic intent  -> Figure Intent / family contracts
reusable visual detail  -> deterministic runtime
rendering primitives    -> Matplotlib
quality boundary        -> validation + tests + release gates
```

Do not add new public plotting capabilities, templates, Figure Intent fields, low-level visual APIs, or third-party plotting backends in this round.

# Part II — Architecture-enforcement tests

## 4. Add executable architecture contracts

The key goal is to make the intended architecture fail in CI when future changes violate it.

Prefer a standard architecture-test tool when it provides clear value. Evaluate **Import Linter** first. If it can express the contracts cleanly, add it as a dev dependency and CI gate. If it requires brittle or artificial configuration, implement focused repository tests instead and explain why.

At minimum enforce these contracts:

### 4.1 Production isolation

`src/axiomfig/` must not import from:

```text
tests/
scripts/
gallery/
reports/
examples/
```

### 4.2 Runtime-core independence

Generic runtime modules should not depend on concrete scientific template families.

Audit at least:

```text
config.py
style.py
layout.py
ornaments.py
typography.py
rendering.py
validation.py
latex.py
```

They may operate on generic Matplotlib/AxiomFig objects and metadata. They should not import, for example, `axiomfig.templates.omics` or `axiomfig.templates.association` unless a real architecture requirement exists and is documented.

### 4.3 Cross-family isolation

One scientific family should not import another family's private adapter/builder implementation merely for convenience.

Shared behavior must move only when there are at least two genuine consumers and a clear generic owner.

### 4.4 Evaluation isolation

Production must not import benchmark/evaluation logic.

The following remain evidence infrastructure only:

```text
tests/evaluation/
gallery/capability_audit/
gallery/archive/
reports/
```

### 4.5 Public boundary integrity

Tests must verify that Figure Intent remains the only formal user/Agent execution schema. No production `ElementIntent`, arbitrary visual-option bag, backend switch, or parallel adjustment schema may appear.

### 4.6 Contract ownership

Tests should verify that:

```text
template identity -> index.yaml
scientific required/optional fields -> family contract.yaml
visual numeric defaults -> packaged style/font/color YAML
```

are not duplicated as competing production tables.

Do not misclassify `TEMPLATE_BUILDERS` as duplicate scientific truth: it is an explicit executable binding and is valid when its equality with the declarative registry is checked.

### 4.7 Repository-boundary checks

Programmatically reject production/release contamination by:

```text
absolute local paths such as /Users/... or /home/...
committed tmp/cache/build artifacts
unexpected very large files outside intentional fonts/Gallery artifacts
private-data-looking paths
benchmark outputs in src/
```

Use explicit allowlists where the repository legitimately contains Gallery PDFs/PNGs and bundled open fonts.

# Part IV — Strict structured-input and bounded failure semantics

## 6. Harden YAML/JSON/CSV input boundaries

The public input boundary must fail closed and emit bounded domain errors rather than implementation exceptions.

Audit every use of YAML/JSON/CSV loading in production.

### 6.1 Duplicate YAML keys

Reject duplicate mapping keys in all project-owned YAML that affects execution, including where applicable:

```text
Figure Intent YAML
style.yaml
fonts.yaml
colors.yaml
templates/index.yaml
family contract.yaml
```

Do not silently accept last-key-wins behavior.

A small shared structured-data loader is allowed if it has multiple real consumers. Keep it narrow. Possible names:

```text
serialization.py
structured_io.py
```

Do not create an oversized utility module.

### 6.2 Bounded public errors

Malformed or user-invalid input should become project domain errors, not raw internal exceptions.

Explicitly probe:

```text
malformed YAML
malformed JSON
empty JSON
JSON root of wrong type
heterogeneous list-of-object JSON rows
missing row keys
empty CSV
CSV header-only
missing dataset columns
unknown template
unknown Figure Intent field
unknown semantic/data role
missing required role
invalid geometry
invalid typography
```

For Figure Intent/data execution, expected failures should be `FigureIntentError` or another narrowly defined public AxiomFig error.

Do not catch every exception blindly. Programmer defects such as logic bugs should still surface during development.

### 6.3 Resource/config errors

Project-owned packaged contracts may raise a dedicated configuration/contract error or a precise `ValueError`; choose one coherent policy and test it. The key requirement is deterministic, informative, bounded behavior.

### 7.1 Figure Intent field combinations

```text

```

```text

```

### 7.2 Dataset structure

Generate small CSV/JSON-equivalent structures with:

```text

extra row keys
empty rows

```

Ensure bounded errors and deterministic column resolution.

### 7.3 Numeric edge cases

Probe controlled values including:

```text

zero
negative values where forbidden
NaN
+Inf
-Inf
```

The system must reject non-finite values wherever the scientific/visual contract requires finite data.

Do not globally reject NaN if a specific supported scientific grammar intentionally owns missing-data semantics; inspect actual families first.

### 7.4 Registry/contract properties

Generate or mutate test-local copies of registry/contract documents to verify:

```text
duplicate template IDs fail
registry-builder mismatch fails
registry-contract variant mismatch fails
invalid input_mode fails
missing contract fails
```

Do not mutate packaged production files in place.

Use bounded Hypothesis settings suitable for CI runtime.
