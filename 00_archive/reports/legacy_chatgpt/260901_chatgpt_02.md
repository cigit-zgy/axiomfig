## Core Bar grammar

The Agent-facing canonical Bar family consists of exactly these 9 core grammars:

1. `simple`
2. `grouped`
3. `stacked`
4. `normalized_stacked`
5. `grouped_stacked`
6. `diverging_stacked`
7. `range`
8. `mirrored`
9. `waterfall`

Expected canonical Agent-facing names:

```text
bar.simple
bar.grouped
bar.stacked
bar.normalized_stacked
bar.grouped_stacked
bar.diverging_stacked
bar.range
bar.mirrored
bar.waterfall
```

Follow existing dotted Agent-facing versus slash runtime naming conventions.

### simple

Schema:

```text
category | value
```

Logical key: `unique(category)`.

One value per category. Signed values are valid. Vertical/horizontal is a semantic orientation modifier, not a separate data grammar.

### grouped

Schema:

```text
category | group | value
```

Logical key: `unique(category, group)`.

Multiple side-by-side groups within each category. Same schema for vertical/horizontal orientation.

### stacked

Schema:

```text
category | component | value
```

Logical key: `unique(category, component)`.

Components are additive within category. Duplicate logical keys must fail rather than be aggregated silently.

### normalized_stacked

Same schema as stacked. Preserve explicit normalization semantics:

```text
normalization = normalize | proportion
```

`normalize` means deterministic within-category normalization of valid additive values. `proportion` means supplied values are already proportions and must satisfy a clear tested tolerance policy; malformed inputs must not be silently renormalized.

### grouped_stacked

Schema:

```text
category | group | component | value
```

Logical key: `unique(category, group, component)`.

Scientific structure:

```text
category -> group -> component stack
```

### diverging_stacked

Schema:

```text
category | component | value
```

Logical key: `unique(category, component)`.

Signed values are allowed. Positive and negative components accumulate independently away from the zero baseline. This is appropriate for Likert/diverging composition and other signed component structures.

### range

Schema:

```text
category | lower | upper
```

Logical key: `unique(category)` and invariant `lower <= upper`.

A range bar is an interval from lower to upper and must remain scientifically distinct from an estimate plus uncertainty interval.

### mirrored

Schema:

```text
category | side | value
```

Logical key: `unique(category, side)`.

The common case requires exactly two semantic sides. Input values remain non-negative. Require a clear semantic `mirror_side` so the runtime knows which side is displayed in the negative visual direction; the Agent must not guess ambiguous side meaning.

### waterfall

Schema:

```text
step | delta | role
```

Logical key: `unique(step)`.

Role vocabulary:

```text
change
subtotal
total
```

Define deterministic cumulative semantics for these roles and reject malformed/ambiguous sequences.

## Shared Bar DataFrame/tabular rules

`bar.md` must teach these common rules:

1. Prefer long/tidy data.
2. Identifier columns (`category`, `group`, `component`, `side`, `step`) are non-null categorical labels.
3. Numeric fields are finite.
4. Each grammar's logical key is unique.
5. Duplicate logical keys fail closed; no hidden aggregation.
6. No automatic mean/median/sum/groupby/statistical reduction.
7. No inference of SD/SE/CI/PI.
8. Preserve first-seen/input category order by default.
9. Orientation never changes the data schema.
10. DataFrame is a conceptual tabular contract; existing CSV/JSON/Figure Intent transport remains authoritative and pandas remains optional/not required.

Include one small table example for every core grammar.

## Modifiers

### Orientation

For grammars where both orientations are meaningful, support semantic:

```text
orientation = vertical | horizontal
```

Default may be vertical. Orientation must not create duplicate canonical scientific grammars.

### Uncertainty

Treat uncertainty as a modifier for point-estimate grammars, especially simple and grouped. Preserve explicit `uncertainty_type`; never infer it.

Prefer clear tabular semantics such as `value/estimate`, `lower`, `upper`, `uncertainty_type`, with a deterministic adapter mapping if the internal builder uses an error-width representation.

Do not invent a stacked-error model in this task.

### Value labels

Retain semantic `value_labels` where supported. Physical placement/padding/font/alignment remain runtime-owned.

### Ordering

Default to first-seen input order. Do not silently alphabetize or sort by value. Avoid a large new ordering API in this task unless an existing executable surface already supports it cleanly.
