## 1. Mission

Implement the agreed **Scientific Figure Element Contract** knowledge layer and test whether it actually reduces LLM decision complexity and/or token cost when a user asks for non-default visual adjustments.

The project already has deterministic defaults in YAML/Python contracts. The purpose of this task is **not** to duplicate those defaults in prose. The purpose is to make non-default adjustments easy for an Agent to locate and apply correctly:

```text
normal request
    ↓
use deterministic defaults
    ↓
no element-contract read required

non-default visual request
    ↓
read one compact element index
    ↓
read exactly one relevant topic when possible
    ↓
find the preferred AxiomFig adjustment surface
    ↓
use only a real AVAILABLE surface
or explicitly report INTERNAL_ONLY / PLANNED / NOT_SUPPORTED
```

The central product question is:

> Does an explicit default → exception → adjustment-surface map reduce the amount of low-level visual reasoning the LLM has to perform, without increasing hallucination, token use, or retrieval fan-out?

This round must answer that empirically with an A/B Agent benchmark.

## 2. Non-negotiable architecture principles

Preserve all current AxiomFig architectural boundaries.

### 2.1 Figure Intent remains the only formal Agent → plotting-runtime boundary

Do not create a second public figure schema.

Do not create:

```text
elements.yaml
figure-elements.yaml
adjustment-intent.yaml
ElementIntent
ElementContract dataclass
new public DSL
```

unless an actual executable production consumer already exists and the repository architecture clearly requires it. The expected implementation is documentation + routing + evaluation, not a second runtime model.

### 2.2 Deterministic defaults retain a single source of truth

Existing files such as:

```text
src/axiomfig/resources/styles/style.yaml
src/axiomfig/resources/styles/colors.yaml
src/axiomfig/resources/styles/fonts.yaml
family contract.yaml files
layout/style/typography runtime code
```

remain the machine-executable sources of deterministic values.

Do not copy stable numeric defaults into multiple Markdown files.

For example, if a marker size is already defined in `style.yaml`, the element contract should reference the configuration path, not restate the numeric value as a second truth.

### 2.3 Agent owns scientific intent; runtime owns low-level visual numbers

The Agent may decide semantic requirements such as:

```text
continuous vs categorical
log scale requested
shared vs panel legend
labels are mandatory
selected data need emphasis
color encoding is continuous
```

The Agent should not invent:

```text
marker s=17
linewidth=0.73
bbox_to_anchor=(1.13, 0.82)
tick length=4.8
manual add_axes coordinates
adjustText force values
textalloc candidate counts
Kiwi strength values
```

### 2.4 External backend names are runtime implementation details

The element contracts may mention an external backend only in a clearly marked developer implementation note when necessary for provenance or future work.

The public adjustment surface must not become:

```text
use_adjusttext=true
use_textalloc=true
use_kiwi=true
```

Backend selection remains deterministic runtime policy.

### 2.5 Progressive disclosure is mandatory

The new knowledge layer must reduce retrieval fan-out.

A normal request that uses defaults should not force the Agent to read element-contract documentation.

A non-default request should normally require:

```text
references/element-contracts/index.md
+ at most one topic file
```

Do not make SKILL.md large.

Definitions:

### AVAILABLE

A user/Agent can express this through an existing supported AxiomFig public route, Figure Intent field, CLI option, or other documented public interface, and it can be executed now.

### INTERNAL_ONLY

The runtime/template implementation can perform the adjustment, but the public Agent/Figure-Intent surface does not expose it as a supported semantic control.

Do not present it as runnable public API.

### PLANNED

The semantic adjustment would be useful and architecturally justified, but no supported executable surface exists yet.

A PLANNED name is a design recommendation, not an API claim.

### NOT_SUPPORTED

The project intentionally has no current or planned public adjustment for this behavior in the present architecture.

Do not invent one merely to make the element table look complete.

## 7. Standard contract format for every element

Use a consistent compact format. Every substantive element section should contain the following information, with wording adapted where needed:

```text
Scientific role
Default behavior
Default source
When to modify
Recommended adjustment surface
Adjustment status
Runtime ownership
Interaction / layout relations
Validation
Implementation note
Avoid / anti-patterns
```

Do not mechanically make every section long. Concision matters.

### 7.1 Scientific role

Explain what scientific meaning the element carries.

### 7.2 Default behavior

Describe the qualitative default, not duplicated numeric constants.

Example:

```text
Use the canonical publication marker geometry and edge treatment.
```

### 7.3 Default source

Point to the executable source of truth, for example:

```text
`src/axiomfig/resources/styles/style.yaml` → `<actual key>`
```

Only cite real keys after code inspection.

### 7.4 When to modify

Describe legitimate semantic or topology reasons for deviating from defaults.

Do not authorize aesthetic whim as a reason for arbitrary low-level tuning.

### 7.5 Recommended adjustment surface

This is the most important section.

List the preferred AxiomFig semantic control or supported route.

Each surface must carry one status:

```text
AVAILABLE
INTERNAL_ONLY
PLANNED
NOT_SUPPORTED
```

For AVAILABLE, give the exact existing field/API/CLI surface.

For PLANNED, clearly label it as a proposed semantic name and do not imply it executes today.

### 7.6 Runtime ownership

State what remains deterministic, such as:

```text
exact physical size
stroke width
packing
measured bbox
exact anchor coordinates
backend choice
connector routing
```

### 7.7 Interaction / layout relations

Use the vocabulary already defined in `references/figure-anatomy.md`, including:

```text
containment
alignment
anchor
minimum_gap
equal_size
shared_edge
shared_axis
aspect
ordering
non_overlap
allowed_overlap
allowed_displacement
z_order
ownership
```

### 7.8 Validation

State what would be a visible/semantic failure.

### 7.9 Implementation note

Matplotlib-specific implementation details may be noted here for developers, but they are not public Agent controls.

### 7.10 Avoid / anti-patterns

Explicitly identify low-level Agent behavior that should not occur.

## 19. Complexity verdicts must be separated

Do not collapse all evidence into one vague statement.

The final report must issue three explicit verdicts:

```text
LLM decision complexity: REDUCED | UNCHANGED | INCREASED
LLM retrieval complexity: REDUCED | UNCHANGED | INCREASED
LLM token cost: REDUCED | UNCHANGED | INCREASED | N/A
```

Then provide:

```text
Overall architecture value: POSITIVE | MIXED | NEGATIVE
```

### Suggested evidence thresholds

Use these as decision guidance, not as a reason to manipulate the benchmark:

Decision complexity can be considered REDUCED when:

- semantic correctness does not materially regress (target no worse than 2 percentage points below baseline), and
- fabricated/low-level adjustment behavior falls materially (target at least 40% relative reduction where baseline incidence is nontrivial), and
- default cases do not gain unnecessary overrides.

Retrieval complexity can be considered REDUCED when:

- treatment meaningfully reduces unnecessary reference fan-out or keeps it tightly bounded while improving correctness, and
- default cases usually avoid element docs, and
- exception cases normally stop after the index + relevant topic.

Token cost can be considered REDUCED only from measured tokens.

Do not call token cost reduced merely because the architecture “seems simpler”.

If treatment improves correctness and low-level safety but uses slightly more tokens, report exactly that. The result may still have POSITIVE overall architecture value.

## 32. Token-efficiency interpretation

Be careful with the phrase “reduce LLM complexity”.

A useful architecture may:

```text
reduce decision ambiguity
reduce hallucination
reduce low-level parameter generation
```

while leaving raw tokens unchanged or slightly higher because one extra focused reference is read.

Therefore the report must explicitly separate:

```text
decision complexity
retrieval complexity
token cost
```

Do not hide an increase in token cost behind a qualitative claim.

Likewise, do not reject the architecture merely because treatment reads one short index if it dramatically reduces low-level guessing and overall errors.

## 38. PASS criteria

A PASS does **not** require token count to decrease.

PASS requires all of the following:

1. the element-contract layer is architecturally clean and progressively disclosed;
2. no stable numeric defaults are duplicated as competing sources of truth;
3. every documented AVAILABLE surface is real and executable;
4. nonexistent APIs are honestly marked INTERNAL_ONLY / PLANNED / NOT_SUPPORTED;
5. the A/B benchmark is balanced and isolated;
6. results are reported honestly even if the treatment is neutral or worse;
7. existing production invariants remain green;
8. the final report clearly states whether decision complexity, retrieval complexity, and token cost improved or regressed.

If the treatment fails to reduce complexity, do not rewrite the result into a PASS narrative. The repository task may still technically PASS if the experiment is valid and the report recommends OPTIMIZE or REVERT based on evidence.

## 39. Final instruction

The purpose of the element-contract layer is not to give the LLM more plotting knowledge to read every time.

Its purpose is to let the LLM avoid low-level visual reasoning when an exception occurs.

The desired architecture is:

```text
      ↓

      ↓

      ↓

      ↓

      ↓
runtime resolves exact visual implementation
```
